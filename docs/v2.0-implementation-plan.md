# Faro v2.0 — implementation plan

Branch: `v2.0` (PR #202, base `dev`). The README in the repo root holds the original intent. This document holds
the decisions and the plan for spreading the work across agents.

## 1. Product decisions (agreed)

| # | Topic | Decision |
|---|-------|----------|
| 1 | Source of truth | **Browser bookmarks are the master copy.** Cross-device sync comes from the browser's own bookmark sync. IndexedDB is a cache plus a store for fields that can't be kept in a bookmark. |
| 2 | Note identity | Derived from the bookmark's content, not from Chrome's bookmark id (see §2). |
| 3 | Fields | `created_at` ← `bookmark.dateAdded`; `domain` ← URL; `source_id` ← `uuidv5(domain + title)`, recomputed on load (same scheme as the old `getsetSource_id`); `prioritised` (star = 5 / archive = −5) encoded in the title; anything else lives only in IndexedDB and **may be lost when rebuilding from bookmarks — accepted**. |
| 4 | Tags ↔ folders | Tags are read from the title into IndexedDB. The folder is then **forced** to match the tags (deepest `a/b/c` tag → `Faro/a/b/c`), as `syncBookmarks` already does. |
| 5 | Scope | **Every** bookmark shows in the extension. A bookmark is moved under `Faro/` only once the user interacts with it (adds a tag, star/archive, or a highlight). Bookmarks outside `Faro/` are never rewritten until then. Firefox is deferred (the hard-coded root id `"2"` is acceptable for now). |
| 5.1 | First highlight on a page | If a plain (non-Faro) bookmark exists for that page URL, the first Faro save **adopts it**: it is updated in place (URL gets the text fragment, title gets the quote and tags) and moved under `Faro/`. Later highlights on the same page create new bookmarks. |
| 5.1a | Original folder on adoption | When a plain bookmark is adopted (first tag, star/archive or highlight), its original folder path becomes a **hierarchical tag**: `Bookmarks bar/Recipes/Italian` → tag `Recipes/Italian` (the browser root is dropped). Encoding rules are in §3.1. |
| 5.1b | Duplicate plain bookmarks | If several plain bookmarks share the URL being adopted, the oldest one (`dateAdded`) is adopted, it **inherits every one of their folder paths as tags**, and the others are deleted (merged into it). |
| 5.1c | Folder tags before adoption | A plain bookmark's folder path is **shown in the dashboard as a read-only tag** (same §3.1 normalisation), so it can be filtered on. Nothing is written to the bookmark until adoption, when the tag becomes a real one. |
| 5.2 | Bookmarks without highlights | Shown in the dashboard with **no quote text**: title and domain only. |
| 6 | Title format / parser | Handed to a dedicated agent (WS-B). |
| 7 | Rangy | **Out of scope, kept as dead code.** Text fragments are the only anchor in v2.0. The rangy serialise/deserialise code stays in the tree (not imported, not deleted) so we can come back to it for dynamic pages (Reddit etc.). |
| 8 | Migration | Ship a release from `dev` first that makes bookmark export **mandatory** (WS-0). Land v2.0 only after all ~5 active users have upgraded and exported. |
| 9 | Website | Bring the landing page back as a plain marketing site describing the v2 features (WS-F). No accounts, no web dashboard. |
| 10 | Layout | The web dashboard goes. All of `shared/` is folded into the extension, which becomes a single package. |

## 2. Note identity (decision 2)

Chrome bookmark ids (`BookmarkTreeNode.id`) are **local to one profile on one device**. Bookmark sync assigns
different ids on each machine, so they can't serve as a note id across devices, and putting a UUID in the title
adds visible clutter. So:

- **Note id = `uuidv5(bookmark.url)`.** For a highlight, the URL carries the `#:~:text=` fragment, which makes it
  unique per quote (`createTextFragment` adds prefix/suffix context for repeated text). For a plain bookmark it is
  just the page URL.
- The id survives tag / star / archive edits (these change the title and folder only), reloads and other devices.
- Two bookmarks with the same URL are the same note. The duplicate is shown once, and the codec / store must keep
  that collapse stable (pick the oldest `dateAdded`).
- Each device keeps a local index in IndexedDB, `noteId → chrome bookmark id`, rebuilt on every full load, so
  writes go straight to the right bookmark.
- Undo/redo patches stay keyed by note id and need no changes.

## 3. Bookmark encoding (starting spec for WS-B)

```
<page title> "<quote>" #tag1 #a/b/c ⭐
<page title> #tag1 🗄️           ← plain bookmark that has been interacted with
<page title>                           ← untouched plain bookmark (any folder)
```

- Order: title, then quote (optional), then tags, then flag. `⭐` (U+2B50) ⇔ `prioritised = 5` (starred),
  `🗄️` (U+1F5C4, written with U+FE0F) ⇔ `prioritised = −5` (archived), no flag ⇔ `0`. The decoder accepts 🗄 with or
  without U+FE0F. Only a **trailing** flag token counts, and only under `Faro/`; a ⭐ elsewhere in a title is text.
- Regexes in the codec use the `u` flag, and whitespace normalisation must not strip U+200D / U+FE0F.
- Parsing works **from the right**: trailing flags, then trailing ` #tag` tokens, then the last `"…"` group if it is
  directly before them. Whatever is left is the page title. This fixes the current bug where a quote with no tags
  after it isn't detected.
- WS-B decides and documents escaping for `"`, ` #`, ` ⭐` and ` 🗄️` inside quotes and titles. Requirements: lossless
  round-trip `encode(decode(x)) == x` for every note we produce, and best-effort decoding of titles written by hand.
- Folder = deepest tag path under `Faro/`. With no tags, a note that has been interacted with sits in `Faro/`.
- **Only titles under `Faro/` are parsed.** Bookmarks outside `Faro/` are decoded as title only, so a page
  title like `C# tips "2024"` is never misread as tags or a quote.

### 3.1 Folder paths → tags (decisions 5.1a / 5.1b): feasibility

This works. Tags were already hierarchical (`a/b/c` ↔ `Faro/a/b/c`), so one folder path maps to **one** tag, not
one tag per level. Folder names, however, can contain characters the title syntax uses:

| Problem in a folder name | Rule |
|---|---|
| Spaces (`Recipes Italian`) | Tags may contain spaces internally. In the title, a tag with a space (or any of `" # !`) is written quoted: `#"Recipes Italian/Pasta"`. Simple tags stay bare: `#recipes`. The `#"` prefix keeps it separate from the quote group. The folder created from the tag keeps the real spaces, so it round-trips. |
| Leading/trailing or repeated spaces | Trim each segment and collapse runs of whitespace (incl. tabs and NBSP) to one space. Small and accepted: the folder name may change slightly when it moves under `Faro/`. |
| `/` inside a name (`AC/DC`) | `/` is the hierarchy separator, so inside a segment it becomes `∕` (U+2215 DIVISION SLASH). It looks the same, round-trips, and the folder is recreated as `AC∕DC`. |
| `"` or `\` inside a name | Escaped inside the quoted tag form (`\"`, `\\`). |
| Empty segment (unnamed folder) | Dropped from the path. |
| Bookmark directly in a root folder | No tag. |
| Case (`Work` vs `work`) | Kept as is; these are different tags, just as they were different folders. |
| Very long titles after many inherited tags (5.1b) | No practical limit in Chrome or in sync; accepted. |

The UI uses the same rules when users type tags with spaces, so typed tags and inherited tags behave the same way.

## 4. Target structure

```
extension/            ← the single package (was sextension/ + shared/)
  src/
    background.ts     ← owns the BookmarkStore; listens to chrome.bookmarks.*
    content.ts        ← selection → text fragment → newNote
    lib/
      bookmarks/      ← codec.ts (WS-B), store.ts + folderSync.ts (WS-C)
      dashboard/      ← moved from shared/src/lib/dashboard
      serialiser/     ← text-fragment code + dormant rangy code
      ...             ← remaining shared/src/lib utilities
    dashboard/, prompt/, App.svelte
site/                 ← marketing site (WS-F), Cloudflare, static
```

Removed: `supabase-sveltekit/`, `shared/` (SvelteKit routes included), `loadSB.ts`, the trpc-to-backend client,
`ActionQueue`, all `@supabase/*` dependencies. The internal background↔content/popup messaging (`chromey/trpc.ts`)
stays if it doesn't depend on the backend.

## 5. Workstreams and agents

Every workstream is handled by one **Opus** agent working in its own git worktree, branched from `v2.0`. I act
as overseer: I hand out tasks, review each diff, and merge into `v2.0` in dependency order. Agents commit per
concern (see the global commit workflow), and only I push.

```
WS-0 (dev)  ────────────────────────────────────────────►  release 0.6.0
WS-A  merge dev + consolidate ──┐
WS-B  codec (pure module) ──────┼──► WS-C  BookmarkStore ──► WS-D  UI + save flow ──► WS-E  e2e pass
WS-F  marketing site ───────────┘ (independent)
```

### WS-0 — mandatory bookmark export (on `dev`, separate PR) — agent 0, start immediately
- In the current extension, force `requestedSync` on (remove the toggle, or make it always on) and run
  `syncBookmarks` at startup and after every change, as it already does after `newNote`.
- Add a one-time notice: "Faro is moving to bookmarks; your notes are now exported to the Faro bookmarks folder."
- Bump the version (0.6.0), build, and check by hand in Chrome that the existing notes show up under `Faro/`.
- Done when: PR open against `dev` and the zip is ready for the Web Store.

### WS-A — foundation (blocks C/D) — agent A, start immediately
1. `git merge origin/dev` into `v2.0`. Resolve conflicts by keeping the v2.0 deletions. Take `dev`'s extension-side
   fixes (e.g. the 200-note display limit). Drop `supabase-sveltekit/` changes, except that a copy of
   `supabase-sveltekit/src/routes/+page.svelte`, the legal pages and the assets they use goes to `site/_from_dev/`
   for WS-F.
2. Fold `shared/` into the extension package (§4). Rename `sextension/` → `extension/`, merge the package.json files
   and fix the `"shared"` imports.
3. Remove all Supabase / backend code and dependencies. Wherever the new store will plug in, leave a typed stub
   (`BookmarkStore` interface, §WS-C) so the extension **builds and loads**, with empty data.
4. Leave the rangy code in `lib/serialiser/` with a header comment `// dormant: kept for dynamic-content anchoring`,
   not imported.
- Done when: `npm ci && npm run build` works, the unpacked extension loads in Chrome without console errors, and
  the dashboard opens empty.

### WS-B — bookmark codec — agent B, start immediately (parallel with A)
- New pure module `lib/bookmarks/codec.ts` with no chrome API, so it can run in parallel with WS-A: `encode(note)
  → {title, url, folderPath}`, `decode(bookmark, folderPath) → Note`, `noteId(url)`, and parse/serialise for flags
  and escaping (§3).
- Replaces `note2Bookmark` / `bookmark2Note` in `bookmarkey.ts`. Its vitest file **imports** the real functions
  (the current test copies the function inside the test file).
- Includes the §3.1 folder-path → tag normaliser (`folderPathToTag(segments)`) and the quoted-tag syntax.
- Cases: no quote, quote without tags, tags with spaces / `/` / `"` / NBSP, `#"…"` next to a `"quote"`, multiple quotes, quotes containing `"` / ` #` / ` ⭐` / ` 🗄️`, unicode and emoji (incl. ZWJ sequences like 👩‍💻 and `U+FE0F` variants such as ❤️), plain
  bookmark titles that contain `#` or `"` (they must decode as a title only), and round-trip property tests.
- Done when: the tests pass, and the format is written into the module's doc comment.

### WS-C — BookmarkStore / sync engine — agent C, after A and B are merged
- `lib/bookmarks/store.ts` replaces the empty `NoteSync.loadFromBookmarks` / `newNote` / `_sub`:
  - **load**: walk the full bookmark tree (all roots), decode every URL bookmark (plain ones get their folder path
    as a derived read-only tag, flagged so it is never written back before adoption), dedupe by note id, fill
    `noteStore`, and merge the fields that exist only in IndexedDB by note id.
  - **write-through**: `updateAct` / tag change / star / archive / delete / undo / redo → apply the patch to
    `noteStore`, then update the matching bookmark (title, URL, `move` to the forced folder). Adoption (§5) happens
    on the first interaction. Deleting a note removes its bookmark.
  - **Adoption** (first interaction with a plain bookmark): turn its folder path into a tag (§3.1). If other plain
    bookmarks share the URL, add their folder paths as tags too and delete them (decision 5.1b). Then write the
    title and move it under `Faro/`.
  - **newNote(quote, url, title, tags)**: run the §5.1 adoption check first, otherwise create a new bookmark.
  - **listen**: `chrome.bookmarks.onCreated/onChanged/onMoved/onRemoved` and `onImportEnded` → incremental update,
    ignoring our own writes (reuse or replace the `dontTrigger` guard). A sync burst from another device must
    end in the same state as a full reload.
  - Folder enforcement (from `syncBookmarks`): after a change, delete `Faro/` folders that are now empty.
    Bookmarks outside `Faro/` are never moved unless there was an interaction.
- Delete the old one-way `syncBookmarks` / hash logic and the `requestedSync` toggle (bookmarks *are* the store now).
- Done when: the e2e checks below pass by hand in Chrome.

### WS-D — UI and save flow — agent D, after C's interface is merged (it can start on the interface stub after A)
- Dashboard: list every bookmark. Plain bookmarks show no quote text (§5.2) and their folder path as a read-only
  tag (decision 5.1c). It can be used to filter but not edited; editing it, or adding a tag, adopts the bookmark. Wire star/archive and tags to the
  store. Remove the login / account / "online" UI from popup and dashboard.
- Content script / prompt: selection → `rangyToTextFragment` → `newNote` with the new signature. Jumping to a note
  opens its fragment URL.
- Rename "Faro" → "Faro Bookmark Manager" where the user sees it, matching the manifest.

### WS-E — end-to-end verification — agent E (or me), after D
Run in a clean Chrome profile with the unpacked build, and ideally a second profile signed into the same Chrome
sync account:
1. Existing plain bookmarks show in the dashboard with no quote; nothing has moved.
2. Highlight text on a page whose plain bookmark sits in folder `Bookmarks bar` → `My Stuff` → `AC/DC` (one
   folder named `AC/DC`) → the same bookmark is updated, gets tag `#"My Stuff/AC∕DC"` and moves to
   `Faro/My Stuff/AC∕DC` (no duplicate). With two plain bookmarks for the page in different folders → one
   bookmark with both tags remains. A second highlight → a new bookmark.
3. Add tag `a/b` → the bookmark moves to `Faro/a/b` and the title ends in `#a/b`. Star → title ends in `⭐`. Undo → reverted.
4. Rename / delete a tag across several notes → titles and folders updated, empty folders removed.
5. Edit a Faro bookmark's title by hand in Chrome's bookmark manager → the dashboard updates.
6. Remove extension data (IndexedDB) and reload → all notes, tags and stars rebuild from bookmarks alone.
7. Second profile: the same notes appear after sync.
8. Dynamic page (e.g. Reddit): saving still works and the fragment link may not scroll. That's a known limitation
   (decision 7).

### WS-F — marketing site — agent F, start immediately (independent)
